# ARCHITECTURE

Purpose: full module map and engine invariants. Read this before changing anything in the engine/domain beyond a card class + its test — new effects, predicates, services, static/continuous effects, `Card` fields, or anything touching networking/frontend.

Gradle multi-module project: a collectible card game with WebSocket-based real-time multiplayer.

## Module Dependency Graph

```
application → webservice → {ai, engine, websocket} → {card, networking, card-data} → domain
              ai → engine
              websocket → networking
application → engine, websocket, ai (config @Imports)
```

- **`magical-vibes-domain`** — Core domain model: `Card`, `Permanent`, `GameData`, `StackEntry`, `ManaPool`, `ManaCost`, enums (`CardType`, `CardColor`, `CardSubtype`, `Keyword`, `TurnStep`), and all `CardEffect` records (in `model/effect/`).
- **`magical-vibes-networking`** — Wire protocol: WebSocket message records (in `message/`), view DTOs (`CardView`, `PermanentView`, `StackEntryView`), and their low-level factory services (`CardViewFactory`, `PermanentViewFactory`, `StackEntryViewFactory`). The engine's `GameViewProjectionFactory` composes those factories into complete player-specific state/join views. The `SessionManager` interface and `Connection` interface live here too; outbound message objects remain typed through both abstractions.
- **`magical-vibes-card`** — Card definitions: each card is a `Card` subclass (organized in alphabetical subpackages like `cards/a/`, `cards/b/`), annotated with `@CardRegistration(set, collectorNumber)`. The project is an umbrella with no sources of its own, split into nested submodules so the ~32k card classes compile in parallel: `:magical-vibes-card:core` (the infrastructure types below plus the two card-local effects `LivingDeathEffect`/`WarpWorldEffect`), `:magical-vibes-card:a` … `:z` (cards by first letter), and `:magical-vibes-card:shared` (cards constructed by a card of *another* letter: back faces, meld partners, conjure targets, together with everything they construct in turn). Letter modules depend on `core` and `shared` but never on each other, since cross-letter references form cycles Gradle forbids; a card in the wrong module fails compilation. Packages are unchanged (`cards.{letter}` is split across a letter module and `shared`), which is fine on the classpath, and consumers depend on the umbrella alone, which re-exports every submodule via `api`. `CardScanner` finds registrations through a ClassGraph metadata scan without loading every card class; each `CardPrinting` holds a lazy constructor factory and loads its class only when a card is actually created. The scanner also records whether the class declares a back face, allowing card-data to instantiate only those few fronts when it builds the back-face lookup. `CardPrinting` stamps `setCode`/`collectorNumber` onto created cards. **This module has no Spring dependency and must keep it that way** — it holds pure card classes. `CardSet` is a plain enum of set codes; what printings exist and what the oracle data says about a set live behind the `CardCatalog` interface, implemented in card-data. Types here that cannot be injected (the `CardSet` and `PrebuiltDeck` enums, whose constants are built in static initializers) take a `CardCatalog` as a **method parameter**; `RandomDeckGenerator` is a plain instance class constructed with one.
- **`magical-vibes-card-test`** — Card tests only, split into `:magical-vibes-card-test:a` … `:z` by starting letter so they compile in parallel and editing a test invalidates only its letter's test task. Each module depends on the whole card umbrella, engine, engine test fixtures and AI: most card tests construct support cards of other letters, so they cannot be isolated by letter, and a card change reruns every card test module. Engine, service, layer, architecture and other non-card tests stay in `magical-vibes-application`.
- **`magical-vibes-card-data`** — Oracle data loading (`com.github.laxika.magicalvibes.carddata`): `CardDataConfiguration`, the `OracleLoader` interface and shared parsing (`TypeLineParser`, `OracleTextNormalizer`, `CardDataSupport`), the server's own set store in `carddata.store` (`SetDataStore`, the `StoredSet` format, and `StoredSetOracleLoader`, the one `OracleLoader`), plus a `SetSource` per provider — `carddata.scryfall` (`ScryfallSetSource`) and `carddata.mtgjson` (`MtgjsonSetSource`). `CardRegistry` (the `CardCatalog` implementation) owns the startup sequence: in `@PostConstruct` it scans the classpath for printings, then calls `OracleLoader.loadSet(setCode, implementedCollectorNumbers)` once per set and performs **every** registration from the returned `SetOracleData` — set name/total on itself, rarity and token images on `CardPrintingRegistry`, oracle data via `Card.registerOracle`. **A loader reads and returns; it registers nothing.** That registration loop used to exist once per provider, hand-synced; keeping it in one provider-neutral place is the point. `implementedCollectorNumbers` is passed in so the loader only maps faces for printings that have a class behind them. Registration also **rejects oracle data that arrived for a class under another card's name** (`verifyOracleNameMatchesClass`): a `@CardRegistration` collector number is typed by hand, and a wrong one is invisible below this layer — the class keeps its engine logic and silently adopts a different card's printed characteristics, while the printing it meant to claim goes unimplemented. Disperse carried M15 #82 (Void Snare) that way and the only symptom was a distant flaky test. The match ignores case and everything a Java identifier cannot hold, and accepts exactly the spellings the card classes use in numbers: an accent folded onto its base letter *or* dropped outright, a legendary named by the part before the comma, and a double-faced class named after its front face alone or after both faces. Anything else is a set-load failure — so a new card class must be named after the card it registers. The `oracle.data-provider` property (SCRYFALL/MTGJSON, case-insensitive, defaulting to SCRYFALL) names the *preferred* provider; `SetDataStore` parses it itself, so a value naming no provider fails context refresh. A source's job ends at producing `RawFace`s — provider-neutral, self-contained, stringly-typed faces — inside a `StoredSet`. **Every rules decision about a face lives in `FaceOracleMapper` and nowhere else** (name splitting, back-face colour indicator, land colour fallback, keyword mapping and narrowing, loyalty/defense/watermark suppression). The split: a source owns *provider quirks* (field naming, face resolution, array ordering, syntax normalisation); the mapper owns *rules policy*. Anything a source does "to match what the other source outputs" belongs in the mapper. That policy existed twice and had already drifted — back faces inherited their front face's keywords on both providers but had been fixed on only one, so Awoken Horror could attack under Scryfall and not under MTGJSON. `FaceOracleMapperTest` pins it against `RawFace` literals with no JSON, and the `scryfall-api`-tagged `ProviderParityTest` holds the two sources to storing the same sets. `SetDataStore` holds the download-once-then-read-from-disk logic, so a source owns only its own HTTP shape and conversion.
- **`magical-vibes-engine`** — The game engine and its Spring wiring (`GameEngineConfig`, `JacksonConfig`). `GameService` (~1700 lines) is the protocol-agnostic game-action API: turn progression, combat, stack resolution, effect dispatch, plus actions like `playCard`/`activateAbility`/`declareAttackers`. `GameSetupService` seats players and runs the opening sequence (custom decks resolved via the optional `CustomDeckSource` interface). The shared card/AI test harness (`GameTestHarness`, `BaseCardTest`, …) lives in this module's `src/testFixtures`.
- **`magical-vibes-websocket`** — WebSocket infrastructure: `WebSocketSessionManager` (implements `SessionManager`), `WebSocketHandler`, Spring config. `WebSocketConnection` is the serialization boundary: it converts typed outbound message objects to JSON immediately before writing a `TextMessage`. Depends on networking for the `SessionManager` interface.
- **`magical-vibes-ai`** — Computer opponents. `AiDecisionEventSubscriber` consumes completed internal game facts and schedules transport-independent `AiDecisionKind` values through each `AiDecisionScheduler`'s delayed/coalescing single-thread executor. The scheduler does not implement the networking `Connection` port. `AiDecisionEngine` reads authoritative live `GameData`, and `AiGameActions` invokes `GameService` with the fixed AI `Player`, so AI seats are never registered as transport consumers. `AiPlayerService` seats an AI via `GameSetupService`. Headless MCTS simulation lives in `ai/simulation`; its isolated session port throws if transport output is attempted. Wired into the app via `AiConfig`.
- **`magical-vibes-webservice`** — Web service layer. `GameMessageHandler` (the `MessageHandler` impl) adapts WebSocket wire messages to engine `GameService` calls (and routes login/lobby/draft/deck to `LoginService`/`LobbyService`/`DraftService`/`DeckService`). `LobbyService` builds lobby views and delegates seating to the engine's `GameSetupService`. Owns the JPA entities/repositories (`User`/`Deck`), the SPA forwarding controller (`SpaController`), and its own `WebServiceConfig` (component-scans `webservice` + `handler`).
- **`magical-vibes-application`** — Spring Boot application (composition root only). Holds just `MagicalVibesApplication` (in its own `application` package so the default component scan picks up nothing else), which `@Import`s each module's config (`GameEngineConfig`, `WebSocketConfiguration`, `AiConfig`, `WebServiceConfig`) and declares `@EntityScan`/`@EnableJpaRepositories` for the webservice module's persistence packages. Owns the runtime DB wiring (Liquibase changelogs, SQLite driver, Hibernate dialect) and `application.properties`. The engine/service unit tests live in this module's `src/test`; card tests live in `magical-vibes-card-test`.
- **`magical-vibes-frontend`** — Angular standalone components. `websocket.service.ts` defines all TypeScript interfaces (`Card`, `Permanent`, `Game`, `StackEntry`) and handles WebSocket communication. `game.component.ts` is the main game UI.

## Key Patterns

- **Saturating P/T, damage and life arithmetic**: power, toughness, damage and life are `int`. Where values can grow without bound (doubling/multiplying effects, P/T sums, damage multipliers, life loss), use `SaturatingMath` (domain `model/`) so results clamp to `Integer.MIN_VALUE`/`MAX_VALUE` instead of wrapping. A saturated value is no longer exact under later arithmetic; this is an accepted deviation.

- **Mutate keeps permanent identity**: `AlternateHandCast.mutate` declares a targeted alternative creature cast. `StackEntry.castWithMutate` sends resolution through `MutationSupport`; an illegal target resolves as an ordinary creature spell. The resolving spell's controller chooses top or bottom through `ChoiceContext.MutateOrderChoice`. A legal merge keeps the existing `Permanent` object, controller, counters, attachments, and combat state, and collects mutate triggers without battlefield-entry triggers. The frozen composite `Permanent.card` supplies copiable characteristics and all component abilities; `mutatedComponentCards` retains physical components in top-to-bottom order for departure. Simulation copies preserve that list, while copying the creature's characteristics creates a single object without its physical components. The top physical component determines token status; token components remain distinguishable when the other component cards move to new zones. Departures count one permanent while moving each physical component. Owners order surviving nontoken components in their graveyard or library through `PendingInteraction.LibraryReorder.destinationZone`; this reorders cards already placed there without repeating zone changes. Pending component orders resume before other input continuations.

- **Stack object identity**: spells use their card ID; each activated or triggered ability has a distinct `StackEntry.getTargetableId()`. The stack-entry copy constructor preserves identity for snapshots and simulations. Use `copyForNewStackObject()` when duplicating an actual trigger. Legacy source-card target IDs are accepted only when they identify one stack object and are normalized before costs are paid.
- **Face-down library casts**: the library-top path evaluates permissions and casting restrictions using the face-down spell's characteristics, pays its face-down alternative cost with the proper cost modifiers, and keeps the original card on the stack with the face-down/disguise flags. The request carries both `fromLibraryTop` and `morph`; free or life-payment casting alternatives cannot replace the face-down cost.
- **Adventure library casts**: `SpellCastingService.playCardFromLibraryTop(..., castAsAdventure)` evaluates permissions, restrictions, timing, targets and cost against `CastingPermissionService.adventureSpellCharacteristics` (the card's identity with only the Adventure's characteristics, CR 715.3a), so an instant/sorcery top-library permission (Johann, Apprentice Sorcerer) allows the Adventure of a creature card. The physical card goes on the stack with `castWithAdventure`, so it is exiled with permission to cast the creature on resolution (CR 715.3d). The request carries both `fromLibraryTop` and `adventure`; `getPlayableLibraryTopCards` offers the Adventure as an extra entry whose `CardView.castAsAdventure` is set.

- **Jackson 3.x**: Import `tools.jackson.databind.ObjectMapper` (not `com.fasterxml`).
- **Domain model is mutable, views are immutable**: `Permanent` has mutable state. View records (`CardView`, `PermanentView`) are created by factory services for serialization — never mutate domain objects for serialization purposes.
- **Derive views with `toBuilder()`, never a hand-listed constructor call**: `CardView` is `@Builder(toBuilder = true)` and the layered pass derives one view from another ~16 times (`PermanentViewFactory` applies granted subtypes/types/supertypes/colors/abilities/text replacements, `CardViewFactory` merges subtypes and graveyard abilities). Each derivation changes one or two components, so it must read `view.toBuilder().component(x).build()`. Re-listing all components in `new CardView(...)` silently drops whatever component is added next — the same drift that bit cast dispatch. Adding a component to `CardView` should be a one-line change plus its projection in `CardViewFactory.create(Card)`.
- **Cards freeze once live**: `Card` objects are shared between the real game and AI simulation copies. They are mutable during construction/assembly but freeze (every mutator throws) once they join a game — deck stamping, `Permanent` or `StackEntry` creation. Runtime state belongs on the `Permanent`, the `StackEntry`, or `GameData` (e.g. imprint: `gameData.get/setImprintedCard`); modal casts mutate a `Card.createRuntimeCopy()`. Enforced by `Card.freeze()` at runtime and `CardImmutabilityArchTest` at build time; tests that tweak a wrapped card's stats use `TestCards.mutableCard(permanent)`. When adding a field to `Card`, also copy it in `Card(Card source)` and bump the count in `CardFreezeTest`.
- **Effect system**: Effects are records implementing the marker interface `CardEffect`. Resolution is class-keyed, NOT `instanceof`: each effect has a `@Component` implementing `NormalEffectHandlerBean` under `service/effect/normalfx/` (it declares `handledEffect()`; `EffectHandlerRegistry` dispatches by `effect.getClass()`). The same class-keyed pattern also drives the **"you may …" accept/decline flow**: each migrated may-ability is a `@Component` implementing `MayEffectHandlerBean` under `service/effect/mayfx/` (declares `handledEffect()`, implements `handle(GameData, Player, boolean accepted, PendingMayAbility)`); `MayEffectHandlerRegistry` dispatches by `effect.getClass()` and `MayAbilityHandlerService.handleMayAbilityChosen` iterates the pending ability's `effects()` in list order, routing to the first one with a registered handler (after its non-effect preambles). The effect-keyed accept/decline **routing** chain has been fully migrated to `mayfx` beans. What remains in `MayAbilityHandlerService` is not routing but state-entangled logic that stays by design: the generic accept path that constructs the stack entry (self-/entering-target wiring), the graveyard target-selection helpers, the CR 603.5 resolution-time may path, and one guarded conditional (Galvanoth's `CastTopOfLibraryWithoutPayingManaCostEffect`, whose branch falls through when its type guard fails). Interface-typed may-effects are keyed per concrete implementor since the registry dispatches by `effect.getClass()` (e.g. `CounterUnlessEffect` → separate `CounterUnlessPaysEffect` / `CounterUnlessDiscardsEffect` beans). **Checklist for a NEW effect** — register its knowledge in the ONE place that owns it, never with a fresh `instanceof`: (1) the record in `magical-vibes-domain/.../model/effect/`; (2) a `NormalEffectHandlerBean` in `normalfx` for stack resolution — OR a `StaticEffectHandler` in `staticfx` for a continuous/static effect (see `LAYER_SYSTEM.md`); (3) IF it carries a target, override `targetSpec()` to return a non-NONE `TargetSpec` (a `TargetPredicates` factory + `harmful` flag + optional `PermanentPredicate`) — the declarative interpreter in `TargetValidationService` offers and type-checks the target; a hand-written `@ValidatesTarget` validator under `service/validate/` is now ONLY an escape hatch for non-structural rules (opponent-relation, controller/owner compare, chosen-source, null-target tolerance), and such an effect still declares its structural spec (see `TRIGGER_SLOT_TARGETING.md` and `EFFECTS_INDEX.md`); (4) IF it belongs to an AI-scored family, implement the matching **capability interface** in `model/effect/` (`DamageDealingEffect`, `RemovalEffect`, `ManaProducingEffect`, `CardDrawingEffect`, `LifeGainEffect`, `TokenCreatingEffect`, `CreatureBoostEffect`, `StaticCreatureBoostEffect`, `KeywordGrantingEffect`, `ControlStealingEffect`, `CounterSpellingEffect`, `RegenerationEffect`) so the AI reads a FACT, not the type (see `EFFECTS_QUICK_REFERENCE.md`). A concrete-effect `instanceof` in an engine/AI file outside `service/effect/**` and `service/validate/**` is the anti-pattern all four steps exist to avoid; no build check enforces it, so it is on the author to route new code through a handler, validator or capability interface.
- **Static/continuous effects**: Computed on-the-fly by the CR 613 layered pass — `LayerSystemService` applies every continuous effect (static slots + floating effects) in layer, timestamp, and dependency order, and `GameQueryService.computeStaticBonus()` assembles the result (see `agent-docs/LAYER_SYSTEM.md`) — then baked into `PermanentView`, never stored on the `Permanent`. The finished board state is memoized per `GameData` behind a structural fingerprint (LAYER_SYSTEM.md §10) — if the layered pass starts reading a new game-state input, extend `LayerSystemService.computeBoardFingerprint` to cover it.
- **Single kill-site for damage (CR 704.5f–h)**: damage code only *records* — marked damage on creatures, the `Permanent.damagedByDeathtouch` flag, loyalty removal on planeswalkers, -1/-1 counters for infect/wither. All resulting deaths are performed exclusively by `StateBasedActionService.performStateBasedActions` (which also enforces 0-toughness, 0-loyalty, legend-adjacent attachment legality, and win conditions) and it runs after every stack resolution, input completion, and combat damage step. Never destroy a creature inline from a damage path; never duplicate the lethality check (`isLethalDamage` is only for combat damage *assignment* validation and excess-damage math).
- **Single gate for losing the game (CR 104.3)**: no code decides a loss on its own. Every site that is about to finish the game because a player lost calls `GameOutcomeService.resolveLoss(gameData, playerId, LossReason)` and branches on the returned `LossOutcome` — only `LOSES` finishes the game, `PREVENTED` and `REPLACED` are distinguished so each caller can word its own log (`resolveLoss` never logs and never finishes). The gate runs the whole chain in order: blanket "can't lose" (Platinum Angel) → the prevention only some reasons allow (Phyrexian Unlife stops `LIFE` but not `POISON`) → every `@Component` implementing `LossReplacer` (`service/outcome/`), so a new replacement card registers by being a bean and no call site learns about it. `GameQueryService.canPlayerLoseGame` / `canPlayerLoseFromLife` are consumed **only** by that gate — `LossDispatchRatchetTest` fails the build on any other engine caller, because hand-rolling the chain is exactly how `StateBasedActionService.checkEmptyLibraryLoss` ended up honoring Platinum Angel while silently skipping Lich's Mirror. Win-side checks ("your opponents can't win the game") use `GameOutcomeService.canPlayerWinGame` and deliberately skip the replacer chain: a win effect ends the game immediately rather than making anyone lose, so there is no loss to replace. `LossReason`'s constants are exactly the replaceable loss events — conceding and an opponent winning are deliberately absent.
- **Replacement ordering (CR 616.1)**: an event several replacement/prevention effects can modify is a `ReplacementEvent` (`model/replacement/`: `DamageEvent` for damage to a player or a permanent, `TokenCreationEvent` for a token creation whose count replacements (Xorn, Doubling Season, Halving Season; `TokenCreationReplacements`) and "those tokens plus ..." additions (Queen Allenal's Soldier, Quina's Frog, Chatterfang's Squirrels, Worldwalker Helm's Map, Stridehangar Automaton's Thopter, Donatello's Mutagen, Tippy-Toe's Food, a solved Case of the Pilfered Proof's Clue, Bilbo's Treasure per Food, and Academy Manufactor's "one of each", which keeps each Clue/Food/Treasure and adds one of the other two kinds; `TokenAdditionReplacements`) the replacements that change what kind of token is created (Divine Visitation's Angels, Fisher's Talent's Shark/Octopus; `TokenKindReplacements`, pure: each rewrites the event's matching token and groups keeping the creating effect's riders; in token-copy events the replaced copies become substitute groups (`TokenGroup.substitutes`, like Jinnie Fay's) that keep the creating effect's instructions but not its copy rider; the created permanents, copies included, are marked `Permanent.tokenKindReplacementsApplied` so `BattlefieldPlacementService` doesn't apply them again) and Jinnie Fay's Cat-or-Dog replacement (`JinnieFayTokenReplacements`: non-pure, its `apply` asks Cat, Dog or original tokens through `ChoiceContext.JinnieFayTokenChoice`, which holds the event and returns `Suspended`; the answer rewrites the event with `TokenCreationReplacementSupport.jinnieFayEvent`, "that many" Cats or Dogs for every token the event creates as it stands, and continues it through `ReplacementOrderService.run`; in a token-copy event the Cats or Dogs become substitute groups, `TokenCreationEvent.TokenGroup.substitutes`, one per copied card (`copyOf` = the card the replaced copies copied, `null` for replaced added tokens), which `TokenCopySupport.createCopiesAfterReplacementOrder` builds with the creating effect's riders, attack target and `instructionRider` card but not the `copyRider`; every `TokenCopySupport` creation is ordered, copies of one card attacking different targets coming from runtime copies of the card so each target keys its own copy group) are ordered by the creating player, resumed through `PermanentControlSupport.applyCreateTokenAfterReplacementOrder`. The event holds the blueprint's count plus `addedTokens` groups (the blueprint's simultaneous tokens and every added token, merged per blueprint in a canonical order so the order additions were applied in doesn't make outcomes differ); a count replacement rewrites every group it applies to, so a doubler applied after Queen doubles her Soldier. An addition's applicability is checked against the event as it stands, so Helm adds a Map once Tippy-Toe's Food makes the event create an artifact token (CR 616.1f). Added blueprints share their abilities through `TokenCreationReplacementSupport` constants (`ActivatedAbility` has identity equality), so equal additions stay equal and an order-independent pair needs no prompt. Only the single-blueprint path of `applyCreateToken` (including `DestructionSupport.createTokenForPlayer`, which delegates to it for Beast Within-style "its controller creates" tokens and opponent-token costs) is ordered, and so is populate: `PopulateSupport.createCopy` creates its copy through `TokenCopySupport.createTokenCopies` (Jinnie Fay asked, copy and added tokens entering together); also Altaïr Ibn-La'Ahad's copies of memory-counter cards, Redoubled Stormsinger's copies of each token that entered this turn, and, with a `tokenRider` for the per-token end-step energy sacrifice, Satya, Aetherflux Genius's copy; `createTokenCopiesChoosingAttackTargetsThen` adds an `afterEntry`, which Calamity, Galloping Inferno uses to run its repeat once every token of the first copy event has entered), `createTokenCopiesAttackingEachOpponent` for copies that each attack a named opponent (Mardu Siegebreaker: each further opponent's copies come from a runtime copy of the card so they form their own copy group with their own `attackTargets` entry; noncreature tokens of a tapped-and-attacking batch only enter tapped), `createTokenCopiesAttackingEachOpponentOrTheirPlaneswalkers` for myriad (the same per-opponent copy groups with `chooseAttackTargets`, so each creature token's `PreparedOpponentTokenCopiesAttacking` entry restricts its choice to its opponent and that opponent's planeswalkers; added tokens take the first opponent's), the first card's copies as the event's own tokens and each other card's copies as a copy `TokenGroup` (`TokenGroup.copyOf`) so a doubler rewrites each card's copies, resumed through `TokenCopySupport.createCopiesAfterReplacementOrder`, and a caller that acts on the created tokens passes its follow-up as the continuation `TokenCopyBatch.afterEntry` through `createTokenCopiesThen` (with an `instructionRider`, `TokenCopyBatch.instructionRider`, given for every token of the event the card it was created for: the copied card for a copy, the replaced copy's card for a Jinnie Fay substitute, `null` for an added token, so per-copied-card instructions such as Mirror Match's "blocking that creature" follow Jinnie Fay's substitutes): it runs once with every entered token, added and substituted ones included, on whichever call the creation finishes (carried through the Jinnie Fay, attack-target and Aura-attachment contexts), and looks permanents up through the game it is given; copies that enter attached to given hosts (Stangg's Aura and Equipment copies, Three Dog's Aura copies) go through `createTokenCopiesAttachedToThen`, whose `copyRider` attaches each Aura copy, doubled ones included, to its copied card's host and which skips an Aura copy that can't enchant its host (CR 303.4g); copies of the effect's own source (`CreateTokenCopyOfSourceEffect`: embalm, eternalize, squad, offspring, ...) go through `createSourceTokenCopiesThen` (the source effect's options mapped onto a `CreateTokenCopyOfTargetPermanentEffect` plus a copy exception; tapped-and-attacking copies choose their attack targets), and encore's per-opponent copies through `createTokenCopiesForEachOpponent`, whose `opponentInstruction` gives every token the opponent it was created for (added tokens the first) (Mirror Match marks each copy as blocking the attacker it copies, and an added Soldier as blocking the first attacker); Human—Time Lord Meta-Crisis chains each player's own creation event from the previous player's `afterEntry` and puts its +1/+1 counters in the last one, while a caller whose follow-up only has to come after the tokens (Lucy MacLean's draw) creates them ordered and splices the follow-up as the next step of its stack entry (`StackEntry.insertEffectsToResolve`), which resumes after any pause; tokens put onto the battlefield attacking (`CreateTokensAttackingEffect`, the tapped-and-attacking forms of `CreateTokenEffect`, `CreateTokenForTriggeringPlayerEffect` and `PayXManaCreateXTokensEffect`) are created ordered first, and `ChooseAttackTargetsForCreatedTokensEffectHandler.createdTokensAttack` splices a `ChooseAttackTargetsForCreatedTokensEffect` step that then makes every creature token of the creation (added ones included) attacking, has its controller choose each one's player, planeswalker or battle (CR 508.4) and schedules any end-step sacrifice — never choose attack targets before the creation; the copy handlers that call `getTokenCreationAmount` themselves keep a fixed order, `LandManaEvent` for a land tapped for mana, including one tapped through Piracy, whose `spellOnly` mana can pay only for spells, `MillEvent` for the number of cards a player mills, whose count replacements (The Water Crystal's bonus, Bruvac's doubling; `MillReplacements`) the milling player orders in `GraveyardService.resolveMillPlayer`: a mill the resolving effect starts is journaled in the effect's `DamageJournal` like its damage (`DamageJournalService.nextMill`; `Slot.Milled` replays the reported cards, `Slot.MillReady` mills the ordered event on the rerun), so a handler that reads the milled cards sees the real ones, while any other mill waiting for its order happens in `GraveyardService.completeMillAfterReplacementOrder` and reports no cards) run through `ReplacementOrderService` (`service/replacement/`). Each effect family is a `@Component` implementing `ReplacementCandidateSource` under `service/effect/replacement/{damage,mana,life,token}/`: `applicable` lists one `ReplacementOption` per effect instance without touching the game, `apply` applies one. The service applies a lone option directly, re-collects after every application (616.1f) and never re-offers an applied key (614.5); self-replacements go first (616.1a). With two or more options it asks the event's chooser through `ChoiceContext.ReplacementEffectOrder` (an ordinary `ColorChoice` list pick) unless every option is `pure` and every order yields the same event. The prompt carries a `ReplacementOptionPreview` per option (the smallest and largest `amount()` still reachable), which the AI uses to order effects. A rider, consumed shield or prompt makes an option non-pure, so it always forces the choice; an option that opens its own decision (Cleric "you may prevent") returns `Suspended`, parks the event in `GameData.suspendedReplacementEvent`, and its handler resumes it. A `CreatureDamageStep` that makes the permanent leave instead of being dealt the damage ("destroy it instead", Kill-Suit Cultist; "if you can't, sacrifice it", Underdark Beholder) declares that departure (`CreatureDamageStep.departs`): the destruction is the modified event, so its own replacements apply before anything happens (CR 616.1f). Before applying the step, `DamageSupport.askBeforeDamageDeparture` asks the departure's destruction and death replacement questions (`DepartureService.askBeforeEvent`); when one opens, the step returns `Suspended` with the step's family in `GameData.suspendedDamageDepartureStep`, and once every answer is in, `InputCompletionService.sbaProcessMayAbilitiesThenAutoPass` calls `DamageSupport.resumeDamageAfterDepartureQuestions`, which applies the step (its departure continues the answered batch through `departNow`) and runs the rest of the event (combat damage then goes on with its step). Damage to a player whose life loss Lich's Duel Mastery would replace with its sacrifice (CR 120.3a) asks that sacrifice's questions the same way once the event's replacements are applied and before it is dealt (`DamageSupport.askBeforeLifeLossDeparture`, from `continueDamage`): the event is suspended with `GameData.askedLifeLossDeparture`, the answered batch waits until the life loss (`finishPlayerDamage`, or the combat step's `applyPlayerDamage`) performs it through `LifeSupport.replaceLifeLossWithShield`, and `DamageSupport.finishLifeLossDeparture` drops a batch the life loss left unperformed. Life loss that isn't damage asks the Mastery's sacrifice only inside a marked handler's rerun window (below): a handler whose first change is a life loss implements `AsksDeathReplacementsFirst` and passes all of its losses to `LifeSupport.applyLifeLosses` (player to amount, computed before the first loss), whose `askBeforeLifeLosses` asks every predicted Mastery sacrifice in APNAP order before any life is lost; every life total change and every Mastery shield put into a hand closes the window, so a later question falls back instead of repeating a loss on the rerun. A handler whose losses follow a change that can alter neither their amounts nor the sacrifice's replacement options (a reveal, a card exiled from a library) computes the losses first and calls `LifeSupport.askBeforeLifeLossesThatFollowAChange` before that change (it asks, then closes the window); a change that can (a sacrifice, an exile from the battlefield), or one the amounts can't be known before (a mill, a random choice, discards), instead inserts the losses as a `PlayersLoseLifeEffect` / `LoseLifeEffect` step after itself. A handler or completion that sets, doubles, exchanges or redistributes life totals (`SetLifeTotalEffectHandler`, the exchange handlers, Reverse the Sands' choice completion through `runAskingDeathReplacementsFirst`) passes each player's new total to `LifeSupport.askBeforeLifeTotalsChange` before the first total changes: a lowered total is a life loss (CR 119.5, CR 701.12c), and a total that rises first would close the window. A "then" handler whose rider is a marked handler's effect (`DestroyTargetPermanentThenEffect`'s "its controller loses 2 life") inserts it, as the resolution step itself, as a `ResolveRiderForPlayerEffect` step carrying the rider's recipient and last-known value; that step's handler is marked exactly when the rider's is (`AsksDeathReplacementsFirst.asksDeathReplacementsFirst(effect)`, which `EffectResolutionService` checks for every marked handler). Damage a resolving effect starts is journaled per effect (`DamageJournal`, opened and closed around every handler by `EffectResolutionService` through `DamageJournalService`): when one of its events prompts, the effect's later damage is held back, the answered event is finished but not dealt, and the effect is resolved again — events already dealt report their recorded result, the answered one is dealt at its own place and the held ones run — so a handler that reads the damage it dealt sees the real amount. Other damage that becomes due while a replacement decision is outstanding waits in `GameData.pendingReplacementEvents`; the input-completion epilogue deals it before a parked resolution continues. `DamageSupport.finishPlayerDamage` / `finishPermanentDamage` own the result stage (life loss, poison, marked damage, loyalty and defense removal, records, triggers), which is not a replacement. Permanent prevention lives once, as the ordered `DamagePreventionService.creatureDamageSteps()`: `applyCreaturePreventionShield` walks them in that order, while the permanent pool offers each as an option. Damage a redirect shield takes over (Harm's Way, `pendingSourceRedirectDamage`) runs through the new recipient's pool: noncombat damage as `DamageEvent.redirectedTo` the new recipient, combat damage as a `redirected` combat event queued in the same damage step (`CombatDamageService.queueRedirectedCombatDamage`), which the step deals with its redirect bookkeeping once its effects are applied; `RedirectedDamageRules.staysSpent` keeps source-side and global effects that already applied spent (CR 614.5), while the new recipient's own effects of a shared family still apply. Combat damage is one `DamageEvent` per recipient per damage step with a `DamagePortion` per source (CR 510.2): `CombatDamageService` collects the assigned damage to the recipients it was assigned to (a guard, an Aura or "dealt to this creature instead of you" is a pool option, `PlayerDamageAbsorber`, that redirects it), runs the events in APNAP order of their choosers, and `DamageSupport.finishDamage` hands each finished event back to `CombatDamageService.recordCombatDamageEvent`, which fills the step's maps for the unchanged result stage. A rule is `Scope.PER_SOURCE` (asked about each portion, one portion at a time) or `Scope.WHOLE` (asked once about the event; a whole prevention leaves unpreventable portions alone). An event that prompts or suspends parks the step through `pendingOptionalDamageChoices`; the answer path calls `continueCombatDamageAfterDecision`. Combat-time side effects that would change the board mid-step (Dralnu, shuffle-after-prevention) are queued on the step state. A land's mana that leaves the pool is final: a color chosen afterwards uses a `ManaColorChoice`/`SpellOnlyManaColorChoice` marked `withReplacementsApplied()`, so "colored mana becomes white" (False Dawn, itself a pool option for lands) is not applied twice. Mana previews and AI planning read a land's replaced mana through `PotentialManaService.landManaPreview` (`LandManaReplacementService.preview` over every order the player may choose). **A new damage or land-mana replacement is a new rule in one of these beans, never another step in a damage path.** Damage multipliers and "that much damage plus N" bonuses are pool options too (`GlobalDamageMultiplier`, `SourceMultiplier`, `SourceBonus` and the recipient-side families), for noncombat and combat damage alike; a bonus family offers one option per effect (`DamageCandidateSource.bonusRule` over `GameQueryService.DamageBonus` lists; a turn-scoped or perpetual bonus is stored as one `DamageBonusGrant` per resolution, never a running total), so a multiplier can be applied between two bonuses: **an effect that deals damage passes the unmodified amount to `DamageSupport`** and combat assignment uses the creature's own damage — `DamageMultiplierRatchetTest` forbids `applyDamageMultiplier`/`applyCombatDamageMultiplier` calls outside `GameQueryService`, where `applyDamageMultiplier` remains a fixed-order prediction for code that reads an amount without dealing it.
- **Competing death replacements (CR 616.1)**: these are not `ReplacementEvent`s. `PermanentRemovalService.deathExileReplacementOptions` lists one `ChoiceContext.DeathExileReplacement` per distinct outcome for a dying creature: hand/library replacements first (Firestorm Phoenix, Gravebane Zombie, Pulmonic Sliver's "may", a card's own shuffle into its library such as Progenitus's `SHUFFLE_INTO_LIBRARY`, Wheel of Sun and Moon's `BOTTOM_OF_LIBRARY` from `GraveyardService.putsCardOnBottomOfLibraryInsteadOfGraveyard`), then one `PLAIN` option for every rider-free exile (pre-removal marks such as Magma Spray, die-level effects, plain graveyard replacements from `GraveyardService.exilesBattlefieldCardPlainlyInsteadOfGraveyard`, including Sanctifier en-Vec's colour exile), then exiles with riders (Kalitas/Gisa-style opponent effects, blood counters, Dauthi Voidwalker's `VOID_COUNTER` and Valgavoth's exile with its source from `GraveyardService.opponentGraveyardExileRiders`, planar life loss, end-step return, source-tracked exile, Void Maw, egg counters, extra turn). A chosen library option is applied by `processGraveyardAndTriggers` itself, so the graveyard pipeline's fixed order of replacements never overrides the choice. With one option nothing changes. With two or more: **state-based deaths** are asked first — `StateBasedActionService` passes each CR 704.3 check's deaths (0 toughness, lethal damage, 0 loyalty, 0 defense, completed Sagas, the world rule, redundant Roles) to `DepartureService.depart` as one `DepartureBatch` (gather: destruction replacements such as regeneration, asked with `RegenerationShieldChoice.inDepartureBatch`; choose: a `DeathExileReplacementChoice` with `inDepartureBatch` per creature, in APNAP order; perform; report). While a question is open `depart` returns `Outcome.Pending` and the batch waits in `GameData.pendingDepartureBatch`; the answer handlers record each answer on it (`DepartureService.record*Answer`), and the next check resumes that batch and performs every death together, each with its chosen option (`PermanentRemovalService.departToGraveyard`). A creature whose only replacement is a granted "may" (Pulmonic Sliver) is asked through the usual may prompt; `PutOnTopOfLibraryInsteadOfDyingHandler` records the answer (`LIBRARY` or `NO_REPLACEMENT`) on the batch instead of moving the creature, so a granted ability whose source dies in the same batch still applies. A prompt raised while a spell resolves parks its later effects (`EffectResolutionService`), so they run after the answer. **Other deaths** (sacrifice, destroy, wraths) are asked before they leave whenever their caller can be stopped and run again (below). A death that needs an answer while its caller can't be stopped is an engine error (see `LegacyDepartureFallback` below); there is no asking after the event. If the death comes from a resolving effect whose handler implements `AsksDeathReplacementsFirst` (it changes nothing before its first removal attempt, e.g. `DestroyTargetPermanentEffectHandler`, `DestroyAllPermanentsEffectHandler`, `SacrificePermanentsEffectHandler`; `grep -rl AsksDeathReplacementsFirst` lists them all), `EffectResolutionService` opens `GameData.deathReplacementsCanRerunEffect` around it; `PermanentRemovalService.askDeathReplacementsBeforeRemoval` (called for a single death and by `DestructionSupport.askDeathReplacementsBeforeSacrifice` for handlers that sacrifice several permanents one by one in the same event) asks every creature with two or more options in APNAP order with `rerunsEffect`, throws `DeathReplacementChoicePending`, and the effect is parked to run again; answers wait in `GameData.chosenDeathReplacementsForRerun` and the rerun's deaths consume them, so the creature leaves inside the effect's own event. Destroy and sacrifice batches (`DestructionSupport.destroyBatch*` / `departDestroyBatch`, `performSimultaneousSacrifice` / `sacrificeTogether`, `SacrificeEachMatchingPermanentEffectHandler`, Make an Example, the sacrificed pile of a pile separation, Scapeshift-style and "sacrifice any number" multi-choice completions) go through `DepartureService.departNow` instead: inside the window the batch asks its destruction and death replacement questions (`inDepartureBatch`, in APNAP order), stays in `GameData.pendingDepartureBatch`, and throws the same `DeathReplacementChoicePending`; the rerun builds the same intents and `depart` continues the answered pending batch, so every member leaves together with its answer and nothing (not even regeneration) is applied before the last answer. Outside the window a batch asks nothing, so a member that needs an answer there is the same engine error. `PermanentRemovalService.tryDestroyPermanent` is a one-intent DESTROY batch too, except for a permanent an enclosing group of simultaneous removals already snapshotted, and so are the other legacy wrappers (`removePermanentToGraveyard`, `removePermanentToPlayerGraveyard`, `sacrificePermanentToGraveyard`, and `destroyPermanentToGraveyard` whose intent says its caller already applied the destruction replacements), except inside any enclosing group of simultaneous removals, while another departure batch is pending, or for a permanent object that isn't the one on the battlefield; those stay inline. A removal that reaches a question it can't ask before the event (competing death replacements, a lone "may" library replacement, competing destruction replacements) is reported to `LegacyDepartureFallback`, which logs its caller and throws an `IllegalStateException`; a card test marked `@FailOnLegacyDepartureFallback` also fails when that error was caught on its way out. `LegacyDepartureWrapperRatchetTest` freezes the wrappers' callers, and no engine code calls them any more (only tests use them to put a permanent into a graveyard directly): **new code builds a `DepartureBatch` and calls `DepartureService.depart`/`departNow`, never a wrapper**. A removal inside `DepartureService.perform` (the Aura that Umbra armor or Crackling Emergence's replacement destroys or sacrifices) is a nested `departNow` batch with the window closed. Answers already in `chosenDeathReplacementsForRerun` answer a batch's question too; a window that closes without its rerun taking the answered batch drops it (`DepartureService.discardAnsweredRerunBatch`). Re-entrant handlers that keep their progress on `GameData` (`TormentOfHailfireEffectHandler`'s deferred batches, `EachPlayerSacrificesPermanentUnlessDiscardEffectHandler`'s collected sacrifices) ask their batch before clearing that progress, so the rerun resumes at the batch instead of repeating earlier steps; a lone candidate sacrificed mid-progress (Read the Runes, `EachOpponentSacrificesCreatureUnlessDiscardEffectHandler`) is asked with the progress pointed back at that sacrifice (`EachPlayerSacrificeOrDiscardState.chosenMode`). A creature whose only replacement is Pulmonic Sliver's "may" is asked there too, through the may prompt (tracked in `GameData.rerunMayLibraryChoices`; `PutOnTopOfLibraryInsteadOfDyingHandler` records the answer for the rerun, or completes a stopped choice again). Any removal, destroy attempt or batch destruction replacement closes the window first, since a rerun would repeat it. Single-permanent sacrifice and destroy choice completions that change nothing before the removal (an edict's `PermanentChoiceContext.SacrificeCreature`, `DestroyChosenCreature`'s destroy mode, the "each player/opponent chooses ... then destroy" contexts, the "sacrifice one of two targets" contexts, the legend rule's "put the rest into the graveyard" (one OTHER batch), a declined champion, Sacred Mesa-style "sacrifice another or this", sacrifice-to-enter and land casualty when not declined, the sacrifice before an Aura is reattached, and the others in `PermanentChoiceHandlerService.killsBeforeChangingAnything`) get the same window: the stopped completion is stored in `GameData.pendingDeathReplacementChoiceReplay`, and once the last answer is in `ChoiceHandlerService` completes the same answer again (`completeChoiceAgainAfterDeathReplacements`) without touching the parked effect; the completion epilogues in `InputCompletionService` close the window. A "you may sacrifice" prompt (the mayfx handlers behind those contexts) whose "yes" leaves a single candidate completes it through the same window with `PermanentChoiceHandlerService.completeLoneCandidateAskingDeathReplacementsFirst` instead of sacrificing it directly. A "you may sacrifice" decline that ends a collected-picks batch (Innocent Traveler, Brain Gorgers) runs through `PermanentChoiceHandlerService.declineAskingDeathReplacementsFirst`, which stores a `GameData.MayAnswerReplay` and re-dispatches the decline through the may handler after the answers; a may answer of either kind whose outcome only sacrifices (Rishadan Cutpurse's unpaid "or sacrifice", Fandaniel/Zoyowa/Braids/Acererak/Star Athlete/Unnatural Hunger/Prowling Pangolin's accepted sacrifice, Vexing Devil's last decline, a forced cost's killing fallback after a decline or an accepted mana cost the pool can't pay, see `MayPenaltyChoiceHandlerService.acceptedCostFallsThroughUnpaid`) uses `answerAskingDeathReplacementsFirst` the same way. A list choice answer whose unpaid outcome only destroys (Erosion's `EnchantedPermanentManaOrLifePaymentChoice` "Don't pay") runs that destruction through `PermanentChoiceHandlerService.runAskingDeathReplacementsFirst` with a `GameData.ListChoiceReplay`, which `ChoiceHandlerService.completeListChoiceAgainAfterDeathReplacements` completes again. A `MultiPermanentChoiceContext.ForcedSacrifice` answer, and the other sacrifice multi-choice contexts in `MultiPermanentChoiceHandlerService.killsBeforeChangingAnything` ("each player/opponent sacrifices ..., then", "keep the chosen, sacrifice the rest", To the Slaughter, Perilous Predicament, attacking-creature sacrifices, Release, Deadly Brew, Stick Together, Winnowing, Tragic Arrogance, Slaughter the Strong; and the "choose, then destroy/sacrifice the chosen" completions: Burning of Xinye's `ForcedDestroy`, Scapeshift, Reprocess-style draws, Mana Seism, `SacrificePermanentsThen`, `SacrificeAnyNumberAndRecordCount`, Phyrexian Dreadnought, and the as-enters sacrifices of devour, Dracoplasm and sacrifice-to-enter), are completed through `MultiPermanentChoiceHandlerService.completeAskingDeathReplacementsFirst` (stored as a `GameData.MultiPermanentChoiceReplay`; earlier players' picks live in the immutable context, so the replayed last answer rebuilds the same batch), as are the attack sacrifice cost (one batch), the unblocked-attacker "destroy the chosen permanent" and the "sacrifice this to destroy" choice. A completion with two removals in a row ("sacrifice it; if you do, destroy ...") opens a second window after the first removal with a replay of only the rest (`SacrificeSelfToDestroy.sourceSacrificed`), so the second removal is asked as its own event. A pile separation whose chosen pile is sacrificed or destroyed (Make an Example, Liliana of the Veil, Do or Die) is completed through `MayAbilityHandlerService.completeKillingPileChoice` with a `GameData.PileChoiceReplay`; the `PendingPileSeparation` is peeked and only polled in the batch's `beforePerform`, so the replay finds it again. A permanent's activated-ability sacrifice costs and `ON_SACRIFICE` abilities ask before payment (`DepartureService.askBeforePayment`, then a `GameData.ActivationCostReplay` / `SacrificeAbilityReplay` is paid again with the answers taken by `takeAnswersForPayment`). So do a hand cast's sacrifice costs: once `SpellCastingService` has validated a cast's costs and before it pays any, `askCastCostSacrificesFirst` asks every permanent the cast sacrifices (`castCostSacrificeIds`); a question stops the cast, puts the card back, and stores a `GameData.SpellCastReplay` (the cast request as plain data), cast again by `completeCastAfterCostSacrificeAnswers`. Every spell cost sacrifice is a `DepartureBatch` through `departNow` (`sacrificeForSpellCost`; several sacrifices of one cost leave together). The other cast paths (graveyard, exile, library-top, plotted, free and morph casts), graveyard- and hand-ability costs and attack and block costs ask the same way before any cost is paid, each with a replay of its own on `GameData`. Prompts raised in a group of simultaneous deaths (`performSimultaneousRemovals`, the state-based death batch) wait in `GameData.deferredDeathReplacementChoices` and open in APNAP order when the group ends (`begin`/`endDeathReplacementChoiceBatch`). The attachment sweeps (`AuraAttachmentService.removeOrphanedAuras` / `enforceAttachmentLegality`, CR 704.5m) leave an Aura whose graveyard move has a question (`PermanentRemovalService.hasDeathReplacementQuestion`) on the battlefield; the state-based departure batch picks it up (`aurasLeftForStateBasedDepartures`) and asks before it leaves. The AI takes the first option. **A new death replacement with a distinct outcome needs an option kind there.** Lich's Duel Mastery's sacrifice, which replaces its controller's life loss once no shield is left (paying life and setting a lower life total are losses, CR 119.4, 119.5), is a departure like any other, so every life change asks it before anything of the change happens: a marked handler whose first change is the loss asks through `LifeSupport.askBeforeLifeLosses` / `askBeforeLifeTotalsChange`; a loss that follows an earlier change it can't alter asks with `askBeforeLifeLossesThatFollowAChange`, or becomes a step of its own (an inserted `PlayersLoseLifeEffect`, `LifeSupport.loseLifeAsStepOfParkedResolution`); answers that pay or lose life run through `answerAskingDeathReplacementsFirst`; costs add the predicted sacrifices (`LifeSupport.successiveLifeLossSacrifices`, one per payment past the shields) to their `askBeforePayment` batch; and an event outside any window (combat damage, a draw, a game-loss replacement that sets a life total) asks through `DepartureService.askBeforeEvent`, the game-loss replacement waiting in `GameData.pendingLossReplacement` until `GameOutcomeService.resumeLossReplacement` resolves it again. An answered event batch still waiting for its event is set aside in `GameData.answeredEventDepartureBatches` when another event in the same step asks, so both are asked before either happens.
- **Damage events of a resolution (simultaneity)**: each effect a resolution dispatches is its own damage event, except that the steps of a `SequenceEffect.simultaneous` share one (`StackEntry.spliceSequenceSteps` records them) and so do slot effects a card adds with `Card.addSimultaneousEffects` (`EffectRegistration.simultaneousWithPrevious`); `StackEntry.damageEventAt` names an effect's event. `EffectResolutionService` calls `DamageSupport.beginDamageEvent` at the top of every effect; when the effect starts a new event, `endOpenDamageEvent` ends the open one first. The open event is `GameData.openDamageEvent`, so a resolution paused for input resumes in the same event.
  - *Combined damage*: while a step of a multi-effect event runs (`GameData.collectingDamageEvent`), `DamageSupport.processDamageEvent` holds the step's own damage in `GameData.pendingSimultaneousDamage` instead of dealing it (damage other damage causes is never held). Ending the event combines the held damage per recipient, source and flags and deals each total as one `DamageEvent`, so a prevention, a "minus 1" or "plus 2" replacement or a "whenever this is dealt damage" trigger applies once, and no step's amount sees what another step dealt (Self-Destruct's power, Form of the Dinosaur). The combined damage has its own `DamageJournal` pass (`DamageJournalService.beginSimultaneousDamage`): when it prompts, the resolution parks on the effect that ended the event (or past the last effect) and runs the pass again on resume, replaying what was dealt. A handler's return value for held damage is the unmodified amount.
  - *Lifelink*: damage one lifelink source deals in one damage event gains life once, so "whenever you gain life" triggers once. Noncombat damage goes through `DamageSupport.checkSpellLifelink`; during a resolution it adds to `GameData.pendingLifelinkGains`, keyed by source and gaining player, and ending the event applies each entry once — before the next effect resolves, and for the last event before the loss check (`endDamageEvent`). Combat sums damage per creature before `CombatDamageService.processLifelink`. Damage outside a resolution gains life right away. A spell's `ON_ANY_SOURCE_DEALS_DAMAGE` reflection batch is keyed by the same event. A new damage path must apply lifelink through `checkSpellLifelink`, never through `LifeSupport.applyGainLife` directly; a new card whose separate effects deal damage at the same time must group them (see `EFFECTS_QUICK_REFERENCE.md`, "Simultaneous damage across several effects").
- **Simultaneous battlefield entry (CR 614.12)**: permanents entering at the same time cannot see each other — a Bramblewood Paragon entering alongside a Warrior does not give it a +1/+1 counter, and an Essence of the Wild entering alongside a creature does not make it a copy. The engine places a batch one permanent at a time, so a caller that puts several permanents onto the battlefield in one event MUST (a) take `snapshotEnterTappedTypes` **once** before the loop and (b) pass the already-placed members as `simultaneouslyEntered` to `putPermanentOntoBattlefield`. `BattlefieldPlacementService`, behind the `BattlefieldEntryService` façade, then hides that whole batch from every battlefield for the replacement-effect window (`hideSimultaneouslyEntered`, restored from a per-player snapshot in a `finally`), which makes batch-mates invisible to every source scan and every condition evaluated in that window at once — no individual applier filters them. Wired at `PermanentControlSupport.applyCreateToken` (covers every multi-token effect), `LibraryChoiceHandlerService.placeCardsOnBattlefieldSimultaneously`, `WarpWorldEffectHandler` + `WarpWorldService` (two separate groups — the enchantment group *does* see the artifact/creature/land group), `ExileAllCreaturesYouControlThenRevealCreaturesToBattlefieldEffectHandler`, `ExileCreaturesFromGraveyardAndCreateTokensEffectHandler`, `LivingDeathEffectHandler`, and `ReturnDamagedCreaturesThatDiedUnderControlEffectHandler`. A new mass-entry effect that skips the batch silently re-introduces the bug; nothing enforces it at build time. Restores replay a snapshot rather than re-adding removed permanents, because battlefield list order is load-bearing (CR 613.7 equal-timestamp tiebreak, trigger stack order, and the index the wire protocol addresses permanents by).
- **Legend rule is a state-based action (CR 704.5j)**: `performStateBasedActions` also runs `LegendRuleService.checkLegendRule` for every player once the destructive passes settle, so no battlefield-entry path needs to remember it (token copies of legendaries are caught here). The check begins a `PermanentChoice` interaction, so it defers itself while another interaction is active/queued or may abilities are pending — the violation is simply re-detected on the next check. The many older `checkLegendRule` call sites at ETB/control-change spots remain as prompt-immediately fast paths; new code should NOT add more, the SBA net covers it.
- **Additional cast costs validate before anything is paid (CR 601.2b/601.2h)**: `AdditionalSpellCostService` (`service/effect/cost/`) is the single home for non-mana additional cast costs — extraction (`extractAndRemove`, feeding the stripped effect list to the stack entry), satisfiability (`satisfiable`, reached by the AI/simulator/playable previews via `CastingCostService.canPayAdditionalSpellCosts`), and per-selection validation (`validateAll` + per-cost validators, all mutate-nothing). Every cast path runs the validation BEFORE the mana payment; the pay methods stay in `SpellCastingService` and each re-runs its validator first. There is no transactional rewind — payments append log entries eagerly — so a throw after partial payment permanently leaks the mana/costs already paid; never add a cost check after a `pay*` call. Successful casting records its canonical state invalidation only after the card is on the stack, cast triggers are collected, and deferred mana-ability triggers are flushed. Cast paths without a wire for a cost's payment selection (cast from exile, cast from library top; graveyard casts for everything except exile-N, sacrifice-a-creature, and single-permanent sacrifice) reject such casts up front rather than casting without the cost. A NEW `CostEffect` type must be classified in `AdditionalSpellCostService.HANDLED_SPELL_COST_TYPES` (with extract/satisfiable/validate/pay support) or in `CostEffectClassificationTest`'s ability-only list — the build fails until it is.
- **Krark's Thumb result choice (stop and rerun)**: a handler marked `ChoosesCoinFlipResultsFirst` (its first coin-flip event comes before any other change it makes) runs with `GameData.coinFlipChoicesCanRerunEffect` set by `EffectResolutionService`; the first `CoinFlipService` flip consumes the flag. If Krark's Thumb's physical flips of that event disagree, the flips go into `GameData.recordedCoinFlips`, the flipper gets a `ChoiceContext.CoinFlipResultChoice` per contested coin, and `CoinFlipChoicePending` stops the handler with `rerunCurrentEffectAfterInteraction` set; once every result is chosen the parked effect resolves again and the flip replays the recorded results. Unmarked handlers, later flips of a handler, and flips outside stack resolution keep the heads result.
- **Input-completion epilogue (parked resolutions)**: when an effect mid-resolution begins an interaction, `EffectResolutionService` parks the stack entry in `GameData.pendingEffectResolutionEntry`; the completion handler that answers the interaction MUST end via an `InputCompletionService` epilogue (`processMayAbilitiesThenAutoPass` / `sbaProcessMayAbilitiesThenAutoPass`), which resumes the parked entry before auto-pass and records the state invalidation only after auto-pass reaches its stable stopping point. A hand-rolled `resolveAutoPass` tail leaves the entry dangling: the spell's remaining effects are silently dropped and `deferPlayerLossCheck` stays wedged. A hand-rolled resume that *does* call `resolveEffectsFrom` is not good enough either: the four variants that existed skipped the pending-may-ability queue, the `GameStatus.FINISHED` guard (Ad Nauseam and Sylvan Library both lose life mid-resolution), the priority-pass clear and the view invalidation, and the scry one auto-passed even when the resumed effects had opened a new prompt. Enforced by `InputHandlerEpilogueRatchetTest`, which requires zero direct `resolveAutoPass` calls under `service/input/` and `service/interaction/` plus the input-answer dispatchers outside them (`PermanentAuctionService`, `ExileSupport`), and probabilistically by `FuzzInvariants.findDanglingResolutionEntry`. Deterministically, `BaseCardTest`'s `assertNoDanglingEffectResolutionPark` `@AfterEach` catches a dangling park in any card test that does not end at a prompt. The mana-ability recipient choice uses the shared no-park completion variant because an overlapping parked entry belongs to its surrounding may-pay flow.
- **Nested prompts for mana abilities during a payment (CR 605.3a)**: `GameService.activateAbility`/`tapPermanent` activate a mana ability inside a payment prompt (may-pay, pay-X, attack tax, block cost) within `InteractionState.openNestedPromptWindow()`. The payment prompt stays active while the activation is validated (so "activate only as an instant" still refuses it); a prompt begun inside the window (the colour of "any color" mana, a land-tap trigger's colour via `AnyColorManaChoiceSupport.beginOrQueueChoice`) suspends the payment prompt with its decision id instead of queuing behind it or overwriting it. Once the nested prompt (and any follow-up prompt it begins) is answered, the `InputCompletionService` epilogue calls `InteractionHandlerRegistry.resumeSuspended`, which restores the payment prompt under its original decision id and re-delivers it — no SBA, queued work, parked resolution or auto-pass runs, because the game is still inside that decision. `GameService.handleInteractionAnswer` resumes it too if a handler ends without the epilogue.
- **Interaction prompts project from live state, so a prompt can be refined after `begin`**: `GameEventProjectionSubscriber.projectDecision` reads `gameData.interaction.activeInteraction()` at dispatch time — after the outer action completes and the monitor is released — not from the `DecisionRequested` fact. An action may therefore refine the record an inner service already began, up until it returns, and both the first delivery and every reconnect replay see the refined version. `InteractionState.replaceActiveInteraction` is the only supported way to do it and deliberately keeps `activeDecisionId`: the refinement must be **presentation-only**, never a change to what is being decided or to the set of legal answers, or reconnect replay and answer matching break. The one user today is `ManaChoiceNarrowingService`, wired into `GameService.activateAbility`/`tapPermanent`: it greys out the mana colours that would strand the payment the client declared via `ManaPaymentIntent` (the MTGO-style hold-back flow is client-side, so the engine has no payment session of its own and needs the intent passed in). The intent's mere presence also marks the tap as part of a payment, which holds the mana ability's non-mana triggers until the spell or ability is put on the stack; a tap with no intent puts them on the stack at once ("Mana-ability trigger timing" in `ACTIVATED_ABILITY_GUIDE.md`). Viability is decided by reusing `PotentialManaService.buildVirtualManaPool` + `GameActionAvailabilityService.isCardPlayable`/`ManaCost.canPay` rather than a second mana solver, and every greyed option stays legally answerable — `ChoiceHandlerService` never consults `disabledOptions`.
- **Single wire→engine cast dispatch**: `PlayCardRequestDispatchService` is the only translation from `PlayCardRequest` to `GameService` cast calls, shared by `GameMessageHandler` (backend) and `AiGameActions` (AI). Never re-inline the field-by-field dispatch in an adapter — two hand-maintained copies drifted twice (dropped `discardHandCardIndex`; flashback branch missing tap/retrace payments). A new `PlayCardRequest` field is threaded through in that one class only.
- **Thread safety**: `GameData` uses `ConcurrentHashMap` + `synchronized(gameData)` blocks in `GameService`. Validation checks must go INSIDE synchronized blocks.
- **Domain events**: Mutable `GameData` remains authoritative; it is not event-sourced. `GameMutationCoordinator` records immutable transport-independent facts under the game monitor, allocates deterministic game-local action/event sequences on successful completion, releases the monitor, and then dispatches. `GameService`, setup/join (including AI and tournament games), and timeout callbacks own outer actions; nested work joins weakly keyed per-game action state and never uses `ThreadLocal`. Human output flows through `GameEventProjectionSubscriber` → typed messages → `GameMessageTransport` → connection serialization. AI wake-up flows through `AiDecisionEventSubscriber` → `AiDecisionKind`, never networking messages. Audience is explicit, hidden information defaults internal-only, simulation batches suppress every subscriber, and reconnect derives current state/current interaction through an ordered read-only observation. `GameViewProjectionFactory` builds only requested human views. `GameActionAvailabilityService` is the shared transport-free playability query. `GameMessageTransport` and `GameSessionTransportAdapter` are the only engine services allowed to depend on `SessionManager`. `GameLogService` alone appends structured logs and records index-only facts; projectors derive incremental log output from those facts and never write projection cursors into `GameData`. Event subscribers never mutate authoritative game state. See `agent-docs/DOMAIN_EVENTS.md` for the complete contract and permanent build invariants.
- **Frontend signals**: `game = signal<Game | null>(null)`, updated via spread + `game.set()`. RxJS Subjects for WebSocket messages.

Source-controlled damage triggers use `EffectSlot.ON_CONTROLLER_DEALT_DAMAGE_BY_ALLY_SOURCE`, dispatched only when the damage source is controlled by the damaged player. `DamageTriggerCollectorService` snapshots the damage amount into the trigger entry, and targeted effects continue through the normal triggered-ability target pipeline.

## Oracle Data

All card metadata (name, type, mana cost, color, supertypes, subtypes, card text, power/toughness, keywords) comes from `StoredSetOracleLoader`, driven by `CardRegistry`. It reads each set from `SetDataStore`, which keeps the server's own provider-neutral copy of every set as `set-{code}.json` in `card-data.cache-dir` (`./card-data-cache/` by default; the file is named by the requested code, so MB1 is `set-mb1.json` although its data comes from CMB1). A `StoredSet` holds **every** printing of the set, implemented or not — collector number, rarity, face names, front/back `RawFace`s and split halves, the `PrintVariant` (promo types, frame effects, border, full art — Scryfall's vocabulary) and format legalities — plus the token list, the provider it came from and when it was fetched. Faces are stored *before* `FaceOracleMapper`, which runs on load, so a rules-mapping fix needs no re-download. When a set has no file, or one whose `formatVersion` is not `StoredSet.FORMAT_VERSION`, the store downloads it into a fresh temp directory from the preferred provider, retrying transient I/O failures; if that provider still fails it uses the other one and logs a warning. It then writes the converted file atomically and deletes the temp directory, so only the server's own file is ever kept — never a provider's JSON. If both providers fail, nothing is written and the load fails. The fallback only ever affects a set's first fetch: the stored file pins the data from then on, and its `source` field records which provider it came from. Nothing refreshes a stored set — not oracle text, not legality (`DeckLegalityRegistry` reads it once per set); deleting the file is the only way to re-download it. Bumping `FORMAT_VERSION` re-downloads every set and needs a new GitHub Actions cache key. Gradle test tasks prefer MTGJSON and point every test JVM at the repository-root cache, which GitHub Actions restores and saves between runs; an explicit system property can still prefer another provider. The card browser and deck builder (`CardBrowserService`) list a set from the same `StoredSet`, so they show the same cards whichever provider a set came from. MTGJSON does not tag planeswalker-deck printings, so `MtgjsonSetSource` adds `planeswalkerdeck` to a printing that has no promo types and is found only in decks (`boosterTypes` contains `deck`). Aftermath cards are split cards (CR 702.127a): under either provider's layout (`split` or `aftermath`) the front face maps to the whole card, with both names and the combined mana value (CR 709.4a/b), so off the stack Commit // Memory is named "Commit // Memory" and has mana value 10. Card subclass constructors contain only game-engine logic (effects, abilities, targeting) — metadata is auto-populated from the registry via `Card`'s no-arg constructor. Production uses the default `EAGER` load mode and registers every set during `CardRegistry` initialization. `GameEngineConfig` does not import `CardDataConfiguration`; each outer context does (the application, `GameTestDoublesConfig`). The headless MCTS context (`HeadlessSimulationContext`) instead reuses the application's `CardRegistry`, `RandomDeckGenerator` and `DeckLegalityRegistry`, which `HeadlessSimulationCardDataSharing` hands it at startup, so the first hard-AI game does not load every set a second time; with nothing shared (standalone AI tests) it builds card data of its own. `GameTestEngineContext` currently selects `ON_DEMAND`: `@CardUsed` on a `BaseCardTest` class or method preloads the set containing the most declared cards, then repeats for any cards not covered by that set, while catalog lookups and the optional oracle-miss resolver remain as compatibility paths for tests not migrated yet. `EXPLICIT` installs no resolver and is the target mode once every card test declares all concrete card classes it constructs. Each set is loaded at most once per test JVM; the first request may fetch from the provider, and later requests reuse the disk cache and registered data. Split cards retain the provider's combined mana value through `RawFace` and `FaceOracleMapper`. `FaceOracleMapper.toSplitCardOracleData` also gives the whole card both halves' types and colours (CR 709.4b/c) and attaches each half's own name, cost, types and colours as `OracleData.splitHalves` (Scryfall `card_faces`, MTGJSON side entries), which `Card.getSplitHalves()` exposes. A split card's halves are modes of one `ChooseOneEffect`, listed in printed order; when a single mode *i* is chosen, `SpellCastingService` applies half *i*'s characteristics to the runtime copy for the timing check, cost payment and the stack (CR 709.3a/b), so split cards need no `withSpellType`. Before the half is applied, `Card.rememberSplitWholeCard()` stores a frozen snapshot of the whole card as `splitWholeCard`. `StackEntry.getPhysicalCard()` returns it, so every stack exit (resolve, counter, fizzle, exile, return to hand or library) moves the whole card with its combined characteristics (CR 709.4). A copy with a fresh identity drops the snapshot. The mode's `withManaCost` still marks a cost-bearing mode and is the fuse mode's total cost; the fused spell keeps the whole card's combined types (CR 702.102b). Every cast of a split card during resolution or through a "you may cast" permission goes through `SplitCardCastSupport` (hand, graveyard, library top, exile, outside the game, and revealed cards held outside every zone). It offers only halves that can be cast: within the cast's mana value cap and allowed-halves list, with a legal set of targets, whose cost the caster could pay from their pool and mana sources on a paid cast, and the fused spell only from the caster's own hand on a card with the `FUSE` keyword. The player chooses the half, announces X when a paid half's cost has {X} (a free cast leaves X at 0), chooses targets, and only then is the cost paid and the card moved to the stack (CR 709.3, 601.2b-h). A card set aside from its hand, graveyard, library or outside the game goes back if the cast fails. `SplitCardCast.Origin` covers the other cases. `ExileCast` (through `beginFromExile`) keeps the card in exile and pays the half's cost through `SpellCastingService.payResolutionExileCastCost`; a copy that isn't cast ceases to exist, and a card can go to its owner's hand instead. `RevealedCast` puts an uncast revealed card in the graveyard or on the library bottom. `OutsideGameCast` pays a sideboard cast's tax. `WordOfCommandCast` leaves the card in hand and casts it through `playCard` with the half as its mode and the announced X. `alternativeManaCost` pays a miracle cost instead. `CopySupport.createCopyCard` keeps a split card's halves and combined mana value (CR 707.2). The exile free-cast queue (cascade) and library casts choose the half through their own mode choices, never offer the fused mode (`SplitCardCastSupport.isFusedMode`), since fuse applies only from a hand (CR 702.102a), and apply a "spell with mana value N or less" limit per half. Every cast path ends in `SpellCastingService`'s mode unwrap, which refuses the fused mode on a card without `FUSE` and refuses a fused or `ChooseOneOption.handOnly` mode unless the card is cast from its owner's hand — inferred from the card still being in the caster's hand, or passed by a `SplitCardCastSupport` cast, which has already set the card aside. `ModalOptionView.handOnly` marks those modes so the client offers them only for a cast from the hand. A permission worded "cast a spell with [characteristics]" checks the half being cast (CR 709.3a); one worded "cast a card with [characteristics]" checks the whole card (CR 709.4). `isSplitCard` excludes Rooms, which are cast as permanent spells with a door. Aftermath halves are back-face classes and get their own oracle data as back faces. `Card.isAftermathSplitCard()` marks the whole card; `StackEntry.getCard()` gives an aftermath spell with no explicit cast card only the half being cast — the first half (`Card.applySplitHalf` on a frozen copy) or, when cast with flashback/aftermath, the graveyard half — so every cast path sees that half's name, types, colours and mana value on the stack (CR 709.3b) while `getPhysicalCard()` stays the whole card. Name matching against a chosen name uses `Card.hasName`, which accepts either half's name (CR 709.4a).

## Trigger and entry state

Clone entry replacements can retain a prepared permanent in `CloneOperationState`, preserving its identity, zone provenance, and ownership while copy choices are answered. Any entry that reaches `BattlefieldPlacementService.place` without having been offered its "enter as a copy" replacement (library searches, reanimation, graveyard and exile land plays, other direct puts) pauses there through `CloneService.beginEntryCopyChoice`; `CloneOperationState.entryRequest` keeps the original `BattlefieldEntryRequest`, and the answered copy re-enters `place` with it. `Permanent.copyEntryResolved` marks entries whose choice was already offered — Clone completion and every member of a `BattlefieldEntryBatchSupport` batch — so they are not asked twice. Only one copy choice is open at a time; an entry reaching placement while one is open (the second of two Clones entering together) waits in `GameData.pendingEntryCopyChoices` and is offered its own choice once `CloneService.beginNextQueuedEntryCopyChoice` finds `cloneOperation` free (after a copy entry completes, or from `InputCompletionService`). Each pending choice records the permanents on the battlefield as it entered (`CloneOperationState.copyablePermanentIds`), so a copy can't pick a permanent entering with it or after it. A library reveal-and-put choice (Collected Company) that leaves a copy choice open parks the unchosen cards in `PendingLibraryRevealRemainder`; `InputCompletionService` hands them back to `LibraryChoiceHandlerService.resumeLibraryRevealRemainder` once no copy choice is open or queued. Whiskervale Forerunner's battlefield-or-hand reveal parks its unchosen cards the same way until that choice, and any copy choice it starts, is answered; Zimone's Experiment puts its unchosen cards on the bottom before its lands enter, as its Oracle text orders. When a spell resumes after that entry, its returned-permanent reference uses the copied characteristics, with last-known characteristics retained if the permanent leaves before the continuation.

`BattlefieldEntryBatchSupport` gathers Aura attachments, battle protectors, Clone copy choices, and native entry choices before placing a simultaneous batch. `CloneOperationState.battlefieldEntryBatch` returns a prepared copy to that batch instead of entering it immediately. `GameData.pendingBattlefieldEntryBatch` and `pendingBattlefieldEntryRequests` retain the pending batch and answered requests for Riot, Unleash, Amplify, naming, entry costs, and conflicting tapped-entry choices. Their completion handlers resume preparation rather than entering one member alone. All physical cards remain in their original zones during these choices, including the entire revealed library prefix in its original order. After placement, `BattlefieldEntryLibraryRemainder` removes its exact skipped card IDs and returns them to the bottom or shuffles the library. Simulation copies isolate both active choice payloads and pending batches; resumption replaces the candidate and saved request with the answered prepared permanent.

Multi-card puts that choose their cards one at a time collect every choice before any card moves, then enter through one `BattlefieldEntryBatchSupport` batch, so each entrant's triggers see the others (CR 603.6a) and each Aura's controller chooses what it enchants as it enters (CR 303.4f) among objects already on the battlefield, never a card entering with it. "Put any number of cards from your hand" (`PutCardToBattlefieldEffect.putAnyNumber`) keeps the picked cards in hand, listed in `GameData.pendingAnyNumberHandPutCardIds` and left out of later valid indices, until the player declines or no match remains; face-down puts pass a prepared face-down permanent, which skips Aura, Siege and naming choices and gets face-down entry triggers. A `LibraryRevealChoice` that puts its chosen cards onto the battlefield returns them to the library and enters them as one batch unless it is cloaked, has an entry replacement or a battlefield-selection follow-up, or a chosen card still sits in some zone; a card that can't enter stays in the library. A `PendingGraveyardReturnBatch.heldInGraveyard` batch (Gruesome Menagerie) leaves chosen cards in the graveyard, so graveyard indices stay stable, and enters them together once the return queue empties. `GraveyardReturnSupport.beginGraveyardReturnQueueAsOneEvent` wraps a queue of graveyard choices in one graveyard-leave batch (`GameData.graveyardReturnQueueLeaveBatchOpen`), so "one or more cards leave your graveyard" triggers once (Grave Sifter).

Each-player choices follow CR 101.4: every player chooses in APNAP order, then the chosen cards move together. Each-player discards set `GameData.deferredDiscardChooserId` for the current chooser; that player's `DiscardChoice` answers only record `deferredDiscardSelections` (no discard event opens), and the effect calls `CardChoiceHandlerService.discardDeferredSelections` once the last player has chosen (Mog, Moogle Warrior; Borderland Explorer; Strongarm Tactics). Each-player exiles from hand (an `ExileFromHandChoice` with `remainingChoosers`) move each pick into `GameData.stagedHandExiles`, out of the hand and unlogged, and exile the whole batch after the last pick, firing each player's cards-exiled-from-hand triggers once (Mind Swords). `PutCardsOntoBattlefieldTogetherEffect` sets `holdingHandBattlefieldPuts`, so its steps' hand picks wait in hand in `heldHandBattlefieldPuts` and then enter through one `BattlefieldEntryBatchSupport` batch.

"One or more … enter" triggers group by `GameData.collectingSimultaneousCreatureEntryTriggers` (despite the name it covers lands too): while it is set, a source's batched ability that already triggered for this event adds later entrants to that trigger's `triggeringPermanentIds` instead of triggering again. `BattlefieldEntryBatchSupport.placeCards`, the graveyard return-all paths, Living Death and the conjured-duplicate handler set it around their trigger collection; a new mass-entry path that skips it triggers a batched ability once per entrant.

Perpetual base power and toughness setters use `GameData.perpetualCardBasePowerToughness`, keyed by physical card identity with the original effect timestamp. Layer 7b applies them after characteristic-defining abilities and before additive modifiers; non-battlefield power/toughness queries also honor them. Both game-copy paths retain this immutable state.

Damage events retain snapshots of damaged permanents before state-based actions. On `ON_SELF_DEALS_DAMAGE`, `TriggeringPermanentConditionalEffect` filters these recipients and queues its wrapped effect once if at least one recipient matches, including when the damage source or recipient dies in that event.

Simultaneous death batches snapshot continuously granted `ON_DEATH` abilities before moving any permanent. The snapshot preserves abilities supplied by a paired creature or another permanent dying in the same event and is cleared when that event ends.

A permanent's activated ability keeps the permanents chosen for its sacrifice costs in `GameData.pendingActivationCostSacrificeIds`; they stay on the battlefield (and can't be chosen again) until every cost choice is made. `ActivatedAbilityExecutionService.completeActivationAfterCosts` first asks the CR 616.1 questions of everything the activation sacrifices (those permanents, a `SacrificeSelfCost` source, a `SacrificeSourceEquipmentCost` Equipment, a mana ability's `SacrificeSelfEffect` source) through `DepartureService.askBeforePayment`; when one is asked it stops before tapping or paying anything more, stores a `GameData.ActivationCostReplay`, and is completed again once every answer is in (inside the payment prompt it nested in front of, for a mana ability activated during a payment, CR 605.3a). It then sacrifices them and the source as one `DepartureBatch`, so their dies triggers see each other and the sacrifices consume the answers. A failed activation drops its pending choices. A graveyard or hand card's ability chooses into the same list; `AbilityActivationService.sacrificeChosenCostPermanents` asks first at the top of its completion (`completeGraveyardAbilityActivation`, `completeHandAbilityActivation`, `completeHandAbilityActivationAfterCosts`), stores a `GameData.GraveyardAbilityCostReplay` / `HandAbilityCostReplay` when it asks, and then sacrifices them as one batch (a graveyard ability's sacrifice triggers go on the stack above it, CR 603.3). A spell cast from hand, the command zone, a graveyard (`playFlashbackSpellFromLocation`, including an Adventure cast through it) or the top of a library asks its sacrifices' questions once its costs are validated and before any is paid (`SpellCastingService.askCastCostSacrificesFirst`, refused when the cast's mana, life, log or stack already changed, `CastStartState`): the stop throws `CastStoppedForCostSacrificeAnswers`, the cast path's wrapper stores `GameData.SpellCastReplay` (with the commander being cast, if any), `GraveyardCastReplay` or `LibraryTopCastReplay`, and the cast is made again once every answer is in. A prepared free cast (cascade, cast from exile) asks when its chosen sacrifice is completed (`FreeCastSacrificeCost`, an escalate sacrifice through `FreeCastTapCost`, both in the choice handlers' ask-first lists) and, for "sacrifice all creatures you control", before paying (`askFreeCastSacrificeAllFirst`, the cast paused like a chosen sacrifice). Turning a face-down permanent face up asks before its morph cost's mana is paid and stores `GameData.TurnFaceUpReplay`.

The hand cast and land-play paths read the card through `GameData.castingSourceCards(playerId)`, never `playerHands` directly, so one cast path serves several source zones. `GameService.castCommander` points it at the command zone (`commandCastPlayerId`/`commandCastCardId`); `GameService.playFromHandOf` (`SpellCastingService.playFromHandOf`) points it at another player's hand (`foreignHandPlayPlayerId`/`foreignHandOwnerId`) while Sen Triplets' window (`senControllerPlayerId`/`senControlledPlayerId`, checked by `GameData.canPlayFromHandOf`) is open. The card moves straight from that hand to the stack or battlefield (CR 601.2a). The caster pays every cost from their own pool and hand (`handCostIndex` is -1, so no own-hand card is excluded from hand costs) and uses their own land play. Afterwards the spell's stack entry gets `ownerIdOverride`, so it leaves the stack to its owner's zones (CR 400.3). A land played this way gets `GraveyardReturnSupport.trackStolenCreature`, so it stays with its controller (CR 110.2). A resolving permanent spell whose `ownerIdOverride` differs from its controller is tracked the same way (`StackResolutionService.keepWithNonOwnerController`). The wire carries the hand owner as `PlayCardRequest.handOwnerId` / `ValidTargetsRequest.handOwnerId`; `GameStateMessage.playableOpponentHandIndices` lists the revealed opponent-hand cards the viewer may play (`GameActionAvailabilityService.getPlayableIndicesFromHandOf`). The opponent-chosen-target prompt and plot can't be used from another player's hand.

A player may be able to play from the top of several libraries at once (temporary grants such as Xanathar, or Windriddle Palaces' `AllowPlayFromAnyLibraryTopEffect`). `CastingPermissionService.findLibraryTopOwners` lists every nonempty library open to them (grants first, then every library under an any-library permission, otherwise their own); `findLibraryTopOwner` is its first entry. `getPlayableLibraryTopCards` offers each library's top card with `CardView.libraryOwnerId` set, the client sends it back as `PlayCardRequest.libraryOwnerId`, and `SpellCastingService.playCardFromLibraryTop(..., libraryOwnerId)` checks it through `resolveLibraryTopOwner` (a `null` owner plays the first library); `LibraryTopCastReplay` keeps the owner. `canPlayLandFromTopOfLibrary` finds the library whose top card is the given land. A land played from another player's library gets `GraveyardReturnSupport.trackStolenCreature` (CR 110.2); a spell gets `ownerIdOverride`.

Myriad prepares copies and applies token replacements before choosing a player or planeswalker for each token to attack. `PreparedOpponentTokenCopiesAttacking` holds the prepared batch until every choice completes; doubled tokens have independent choices and enter simultaneously.

`SourceCardInGraveyard` can retain an expected graveyard entry version. Graveyard creature-put triggers bind this version when collected, so leaving and reentering the graveyard cannot satisfy an older Bridge from Below ability.

Delayed graveyard returns use stack entries and `CardIdSetPredicate` with graveyard entry versions.
Divided damage assignments belong to the individual stack entry; copies retain their division
while offering legal replacement targets. Additional ETB abilities on token copies can register
with `TriggerMode.INDEPENDENT` to keep their targets and resolution separate from the copied abilities.

`CharacteristicState.meleeInstances` preserves multiple melee abilities. Each instance triggers
separately and counts players attacked by declared attackers, excluding planeswalkers and battles.
`GameData.lastNormalTurnPlayerId` preserves the normal turn order while extra turns interrupt it.
An exert untap restriction records its resolving controller and expires during that player's
next untap step, even after a control change.
The exert decision happens during attack declaration; accepting it immediately exerts the creature
and queues the resulting reflexive ability for target selection and normal stack resolution.
Separate next-spell-copy effects each create their own triggered stack entry.
Simultaneous spell-cast triggers retain their triggering spell identity. Trigger ordering (CR 603.3b) is one interaction for every batch: once no trigger is waiting for targets or a may choice, `TriggeredAbilityQueueService.beginTriggerOrder` (called from `AutoPassService` before priority and before each combat-trigger auto-resolution) asks each player in APNAP order whose unordered triggers include two or more non-equivalent ones to place them from the bottom upward via `ChoiceContext.TriggerOrder`. Entries are reordered only within the positions that player's batch already occupies. `StackEntry.triggerOrderChosen` marks every trigger that has been through ordering (and everything on the stack when the top resolves) so it never joins a later batch; it survives simulation copies. Players in `GameData.playersAutoOrderingTriggers` keep the order the triggers were collected in without a prompt — the test harness enables this for both players by default (`harness.setAutoOrderTriggers(player, false)` to test ordering).
Divided-damage, divided-prevention and divided-counter triggers (`DealDividedDamageEffect` with `etbAssignments` and no target restriction, `PreventDividedDamageEffect` with `etbAssignments`, `DistributeCountersAmongTargetsEffect` in `CHOSEN` mode with `etbAssignments` and no target restriction, e.g. Glint Weaver) that reach the stack without a division announce it before priority: `AutoPassService` calls `StackedDividedDamageTriggerService.announceNextDivision` right after `StackedModalTriggerService.announceNextMode`. A staged `pendingETBDamageAssignments` buffer is taken over; otherwise the controller picks one to `maxTargets` targets (`MultiPermanentChoiceContext.StackedDividedDamageTargets`) and divides through `ChoiceContext.CounterDistributionAssignment` with `stackEntryId` set, which records the division on the existing entry via `StackEntry.announceDamageAssignments`. An entry with no legal target is removed (CR 603.3d).
Delayed damage triggers retain the watched permanent as their damage source. `StackEntry.damageSourceControllerId` preserves that source's controller independently from the delayed ability's controller when the source leaves the battlefield.

Dungeon progress follows the room arrows and offers choices at branches. Bottom-room abilities
complete the dungeon when the last such ability leaves the stack, including being countered.

## Nested games

See [SUBGAMES.md](SUBGAMES.md) for transitions, card transfers, runtime routing, and focused verification.

`GameSession` owns independently mutable `GameData` frames and a stable root identity. Only the active frame accepts player actions. `GameMutationCoordinator` acquires the session lock before the per-game action lock and monitor; `SubgameService` drains transitions after the originating scope completes. Cross-game mutations are sequential, never nested. Suspended parents retain their deferred spell entries. Registry exact-ID lookup remains available to event projection, while `getActive` and player routing follow the active frame. Simulation copies duplicate the complete session and suppress registry/transport side effects.

Outside-game selection uses `OutsideGameCards.view`, which includes eligible cards in suspended ancestors. Removing an ancestor candidate queues a `PendingAncestorTransfer`; the transition service removes it from the actual source and defers ancestor triggers. Do not read `playerSideboards` directly for general outside-game effects.

Queued exile casts with a mandatory discard cost carry a prepared spell in `DiscardFollowUp.pendingSpellCast`. The spell remains outside the stack until the discard payment completes, then the free-cast queue resumes.

`StackEntry.resolutionResults` is the resolution scratchpad: an immutable `ResolutionResults` (the latest removal step's `DepartureResult`s and the latest player picks) that a step writes with `recordDepartures` / `recordPicks` and later steps read through `ConditionContext.resolutionResults()` (`PermanentLeftThisWay`) or the stack entry (`PermanentLeftThisWayPower`/`Toughness`). It is shared by the copy constructor, so a copy taken while the resolution is parked resumes with the same results. A removal step departs through `DepartureService.departAsStep(gameData, entry, effect, batch)`: when the effect is the step itself (`GameData.stepDepartureEffect`, set by `EffectResolutionService` around a top-level handler; a nested dispatch or a second departure of the step doesn't match), a CR 616.1 question leaves the batch pending and owned by the entry (`DepartureBatch.ownerStackEntryId`, its targetable id, so simulation copies find their own parked entry), the handler returns, and the resolution parks at the next step without rerunning. The next `resolveEffectsFrom` first calls `DepartureService.finishStepDeparture`, which performs the batch (logging sacrifices, destructions and indestructible survivors and firing "sacrificed" triggers from its own hooks, then removing orphaned Auras; a batch of two or more permanents is also one leave-the-battlefield batch for "whenever one or more ... leave" watchers) and records its results before the next step resolves. A departure doesn't end its step while the step already waits on another prompt (a damage replacement it dealt): it is departed at once instead. An answered owned batch whose entry is neither parked nor on the stack any more is dropped at the next state-based check (`DepartureService.discardOrphanedStepBatch`). Hooks are rebuilt there, never stored on the batch; owned batches are never taken over or dropped as rerun batches. "Sacrifice it, then ..." and "destroy it, then ..." handlers go through `StepDepartureSupport`: `sacrifice` / `depart` (nothing follows), `sacrificeThenIfSacrificed` (an "if you do" payload, inserted as `ConditionalEffect.unless(PermanentLeftThisWay.sacrificed(), payload)` after the step; resolved at once only from a nested dispatch whose departure is done) `destroy` (a list of permanents destroyed as one event, nothing follows; the handler's last action, so a handler may change the game before it, e.g. pick at random, flip coins, deal damage, counter a spell or clear a chosen value: the chosen-type and chosen-parity wraths, Wild Swing, Metzali, Haphazard Bombardment, Silver Bolt, The Black Arrow, Ouphe Vandals, Rakdos the Showstopper, Consuming Ferocity) and `sacrificeThenContinue` / `destroyThenContinue` / `departThenContinue` (a handler implementing `ContinuesAfterDeparture` runs its own rest at once, or as an inserted `ContinueAfterDepartureEffect` step); what follows reads the departure from the scratchpad (`DepartureResult.lastKnownControllerId`, last-known power, `lastKnownCardTypes`, `lastKnownSubtypes`), never from state captured before it. `DestructionSupport.sacrificeAndLog` (a player sacrifices one permanent; about 60 callers) is a one-permanent `sacrificeTogether` batch that returns its `DepartureResult` (read "if you do" from `sacrificed()` and last-known power from it) and logs and fires "whenever you sacrifice" triggers only for a sacrifice that happened; like `tryDestroyAndLog` it asks only inside a window. `StepDepartureSupport.sacrificeThenIfSacrificed` always inserts its payload as the next step when the sacrifice is the resolution step itself, so a removal in the payload (Blind Zealot's destroy) is its own step with its own window; a nested dispatch still resolves it at once. `DestructionSupport.tryDestroyAndLog` (the many "destroy X, then …" helpers that go on in the same handler) departs a one-intent DESTROY batch through `departNow`, so it asks inside a marked handler's rerun window but never ends a step. A loop ("repeat this process", Tyrant of Discord) departs one permanent per step and, in its `continueAfterDeparture`, inserts its own effect again as the next step. Delayed sacrifices and destroys (`ResolveDelayedPermanentActionEffect`) are step departures too; a trigger's run of them leaves as one batch. A removal that comes after its handler or a choice completion already changed the game (counters put, coins flipped, a random pick) is made a step of its own: `StepDepartureSupport.departAsStepAt` / `departAsNextStep` insert an internal `DepartPermanentsEffect` (and any follow-ups) into the entry, and `departAfterChoice` inserts it where the parked resolution resumes (`pendingEffectResolutionIndex`), so the questions are asked before anything leaves and the earlier changes and random picks are never redone. What a later step acts on besides the departure can wait in the scratchpad's picks: Bend or Break records the lands to tap with `recordPicks` before its destruction step, and its `ContinueAfterDepartureEffect` step taps them; Desolation's damage step reads who sacrificed a Plains from `DepartureResult.lastKnownSubtypes`. A handler that keeps its progress in game state (Plaguecrafter, Eumidian Wastewaker, Forbidden Ritual) departs with `departOrResolveAgain`: as the resolution step it ends the step and inserts its own effect again, which goes on from the saved progress once the departure is done. A prompt answered outside the resolution loop that starts another removal (Forbidden Ritual's accepted repeat) doesn't remove anything itself: it records the answer in that progress and points the parked resolution back at the effect, so the removal starts as the resolution step. Infernal Offering's draws are a `ContinueAfterDepartureEffect` step after its sacrifice step and draw only for the players the results show sacrificed a creature (`lastKnownControllerId`).
